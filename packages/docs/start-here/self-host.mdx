<Note>
  **This documentation describes a self-hosted-only fork.** OpenWork's hosted
  control plane — OpenWork Den, its organization model, the OpenWork Gateway,
  the `openwork-ee` Helm chart, and the hosted inference service — has been
  removed from the repository. There is nothing left to sign up for: you run
  `openwork-server`, you choose your own model provider, and you are done.
</Note>

## What you deploy

One service.

- **`openwork-server`** — the headless backend. Serves the web UI, runs the
  local agent runtime, and holds your workspace state.

There is no second service to deploy. There is no control plane, no account
system, no organization tier, and no sign-in step.

## Install it

```bash
npm install -g openwork-server
openwork-server
```

The server writes its configuration to `~/.config/openwork` and listens on
`127.0.0.1:8787` unless you tell it otherwise. Open the URL it prints and you
are signed in.

<Warning>
  **Do not bind it to a public interface.** The server injects a valid client
  token into the page it serves for *any* `Host` header, and never sends the
  privileged host token to the browser. Anything that can reach the port is
  therefore signed in. Keep it on loopback, or put it behind your own
  authenticating reverse proxy on a network you trust.
</Warning>

For a container image, see [Docker packaging](https://github.com/different-ai/openwork/tree/dev/packaging/docker).

## Connect a model

The server does not ship a model catalog. You configure a provider yourself:

- Bring your own API key for any OpenAI-compatible, Anthropic, or OpenRouter
  endpoint. See [Add a custom LLM](/start-here/connect-your-stack/add-a-custom-llm).
- Run local models through Ollama or any OpenAI-compatible server. See
  [Use local models](/start-here/connect-your-stack/use-local-models).
- Sign in to ChatGPT, or use Gemini and Vertex AI. See
  [Models and providers](/start-here/connect-your-stack/sign-in-with-chatgpt).

If you run a gateway of your own (LiteLLM, Bifrost, or anything else), point the
provider's `baseURL` at it.

### Free inference

The hosted free-inference route is **disabled by default** and has no default
origin. To use a free route, opt in explicitly and name the origin:

```bash
OPENWORK_ENABLE_FREE_INFERENCE=1 \
OPENWORK_FREE_INFERENCE_ORIGIN=https://your-gateway.example \
openwork-server
```

With neither set, the free route resolves to an inert sentinel and makes no
network request.

## Storage and state

- The server keeps workspace and session state on the filesystem, under its
  configured data path.
- It does **not** require a separate database. There is no MySQL, no Postgres,
  and no control-plane schema to migrate.
- Put the data path on durable storage and back it up the way you would any
  other application directory. That directory *is* your deployment's state.

## Authentication

There is no sign-in. The server authorizes the local browser client itself.
`OPENWORK_TOKEN` and `OPENWORK_HOST_TOKEN` are the bearer credentials it uses
when talking to itself; if you terminate TLS at a reverse proxy, make sure that
proxy does not expose the port to untrusted networks.

## FAQ

<AccordionGroup>
  <Accordion title="Can I self-host OpenWork for free?">
    Yes, unconditionally. The entire repository is MIT licensed and there is no
    hosted tier to buy. See [Pricing and licensing](/start-here/pricing-and-licensing).
  </Accordion>
  <Accordion title="Is there a Helm chart or Terraform module?">
    No. The `openwork-ee` Helm chart and the AWS ECS Terraform module were part
    of the removed control plane and are gone. Run the npm package or the
    container image and put your own infrastructure around it.
  </Accordion>
  <Accordion title="Which database does it need?">
    None. State lives on the filesystem in the server's data path.
  </Accordion>
  <Accordion title="Can it use my own models or gateway?">
    Yes, and that is the only supported mode. Configure the provider's `baseURL`
    to point at your gateway. See
    [Add a custom LLM](/start-here/connect-your-stack/add-a-custom-llm).
  </Accordion>
  <Accordion title="Can I share skills and MCP servers?">
    Yes, as files. Skills are directories and MCP servers are configured in the
    UI or config. See
    [Share your setup](/start-here/do-work-with-it/share-your-setup).
  </Accordion>
  <Accordion title="Does it send anything to OpenWork?">
    No. There is no baked-in model catalog, no analytics key, and no default
    control plane. The machine-readable egress allowlist lives in
    `docs/enterprise/outbound-access.json` and is checked against the source by
    `node scripts/check-outbound-access.mjs`.
  </Accordion>
</AccordionGroup>
