Use this page when OpenWork reaches the wrong server, cannot complete TLS, is
blocked by a proxy, or when you need to prove which hosts a locked-down network
actually permits.

<Note>
This fork has no control plane, so there is no cloud catalog to probe and no
admin-triggered diagnostic origin. What remains is the Windows network doctor
and the destination inventory.
</Note>

## Windows desktop network doctor

`scripts/support/openwork-doctor.ps1` is a Windows PowerShell 5.1-compatible,
no-admin, read-only report for IT. It checks DNS, TCP 443, the live TLS
certificate chain with `SslStream`, served certificates with `openssl` when
available, WinHTTP/.NET proxy settings, PowerShell/OS version, and
`NODE_EXTRA_CA_CERTS`.

Run it directly from the raw repository URL when the machine can reach GitHub:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -Command "`$p=Join-Path `$env:TEMP 'openwork-doctor.ps1'; Invoke-WebRequest -UseBasicParsing 'https://raw.githubusercontent.com/sheigl/openwork/dev/scripts/support/openwork-doctor.ps1' -OutFile `$p; & `$p -WebUrl 'https://openwork.example.com' -ApiUrl 'https://openwork.example.com' -ExpectedIssuerMatch 'DigiCert'"
```

If raw download is blocked, copy `scripts/support/openwork-doctor.ps1` to the
machine through your approved offline channel and run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\openwork-doctor.ps1 -WebUrl 'https://openwork.example.com' -ApiUrl 'https://openwork.example.com' -ExpectedIssuerMatch 'DigiCert'
```

Point both `-WebUrl` and `-ApiUrl` at your own server origin. There is no
separate web and API origin in this fork — it is one service on one port.

### Interpreting common verdicts

| Verdict | What it usually means | First fix to check |
| --- | --- | --- |
| `LIKELY TLS INTERCEPTION` | The leaf issuer is an internal or proxy CA instead of the expected public issuer. | Allowlist the host through the proxy, or install the enterprise root in every trust surface that needs it. |
| `LIKELY MISSING INTERMEDIATE OR UNTRUSTED ROOT` | The server may be serving a leaf without the intermediate, or the machine lacks the issuing root. | Fix the server `fullchain`/certificate bundle first, then verify client trust. |
| `MISSING INTERMEDIATE CONFIRMED BY OPENSSL` | OpenSSL could not build the served chain. | Replace the server certificate bundle with a complete chain. |
| `LIKELY DNS ISSUE` | The hostname does not resolve on that machine. | Check VPN state and split-horizon DNS. |
| `PROXY DETECTED` | WinHTTP or .NET routes the URL through a proxy. | Verify proxy authentication, host allowlisting, and expected system proxy behavior. |

## Proxies and Node.js

On Node.js 24.5 or newer, proxy configuration belongs in the process-start
environment:

```bash
NODE_USE_ENV_PROXY=1
HTTPS_PROXY=http://proxy.internal:3128
NO_PROXY=127.0.0.1,localhost,.internal
```

Use `NODE_EXTRA_CA_CERTS` when TLS inspection uses a private root. See
[Certificate trust and proxies](/start-here/certificate-trust-and-proxies).

## Confirming what the network actually permits

Check reachability for every host your deployment needs. The list is canonical
in [Outbound network access](/start-here/outbound-network-access), and in a
default build it is short:

```bash
for host in github.com release-assets.githubusercontent.com registry.npmjs.org; do
  printf '%-40s ' "$host"
  curl -sS -o /dev/null -w '%{http_code}\n' --max-time 5 "https://$host" || echo "UNREACHABLE"
done
```

Then add the providers and MCP servers you have configured. If one of those is
blocked, only that provider or MCP server fails — everything else keeps working.
